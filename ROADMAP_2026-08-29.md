# 6. Insurance / Risk Layer — Future Phase

Secretariat evidence should not be confused with insurance adjudication.

The insurance layer will eventually consume execution observations and historical outcomes to estimate operational risk.

## Principle

> Evidence does not necessarily need to prove every insured event with absolute certainty.

Secretariat should provide high-quality transaction facts and observations.

The insurance/risk layer can use aggregated historical data to estimate:

* event frequency;
* loss probability;
* expected loss;
* severity;
* seller risk;
* endpoint risk;
* agent risk;
* unresolved-event probability;
* recovery success rate.

`UNRESOLVED` is therefore a legitimate observation state, not necessarily a failed transaction.

# 11. Architectural Principles

The following principles should remain stable unless explicitly superseded by a later version:

1. **Secretariat is non-custodial.**
2. **Secretariat never stores client private keys.**
3. **Seller payment is the client's payment, not Secretariat's money.**
4. **Secretariat orchestrates and observes; it does not become the economic owner of the transaction.**
5. **Payment settlement does not prove HTTP delivery.**
6. **Absence of delivery evidence does not automatically prove failure.**
7. **TIMEOUT != FAILURE.**
8. **UNKNOWN / UNRESOLVED is a legitimate state.**
9. **Evidence collection and insurance adjudication are separate responsibilities.**
10. **Risk can be measured statistically across transaction populations.**
11. **Idempotency and recovery must prevent duplicate economic execution.**
12. **Architecture should prefer explicit state transitions over implicit inference.**

# 13. Temporal Trust Boundary -- Requires Further Research

> **Status:** YELLOW Principle established, implementation explicitly deferred
> **Origin:** B8.1-B.2 validity window discussion, August 2026
> **Related to V1.1:** Natural evolution of Evidence Model (S17) and Notary (S26)

## Principle

> Secretariat may define its own canonical operational time domain.
> External timestamps are not automatically considered synchronized with this domain.
> Where cross-domain temporal comparison is required, an offset estimate and uncertainty
> must be established for each external time source -- not a direct identification
> of an external timestamp with local time.

Formally:

    Zeus canonical time:  Z(t)
    External source S:    offset(S), uncertainty(S), measuredAt
    T_Z ~ T_external - offset(S)  +/- uncertainty(S)

## Why This Is NOT Part of V0 or B8.1-B.2

The reason is structural, not merely cautionary. In the non-custodial model (V1.1 S5),
Secretariat is not the party forming the EIP-712 signature -- the client signs.
The formula validBefore = signingTime + maxTimeoutSeconds (confirmed by T1 audit as
reference practice) is computed from the signing party's clock, not Zeus.
Zeus canonical time has nothing to substitute into this field.

**Open question requiring code verification (not assumption):** In Stage A
(AWAITING_PAYMENT_SIGNATURE), does Secretariat pass PaymentRequirements to the
client and let the client compute validAfter/validBefore with its own code --
or does Secretariat propose specific values for signing? If the former (consistent
with reference model and non-custodial architecture), Temporal Trust Boundary
definitely does not participate in signing. If the latter, the question requires
re-examination, but this is a separate verification that does not block the current
B8.1-B.2 decision.

## Where This SHOULD Appear in the Future

Natural placement -- not a standalone "time system" from scratch, but concretization
of what is already abstractly implied:

* **Evidence Model (V1.1 S17)** -- each timestamp in evidence records today is assumed
  "as-is" without explicit offset/uncertainty. A future version could attach
  offset(source) +/- uncertainty to each external timestamp in evidence.
* **Notary (V1.1 S26)** -- "certified fact" today means hash + signature + Notary timestamp.
  Temporal Trust Boundary provides a way to explicitly distinguish "when Notary certified
  the record" from "when the event occurred per external party's claim", with an honest
  measure of uncertainty between them.

Practical value for the future: SLA analysis, timeout analysis, delivery disputes,
forensic audit, insurance-layer disputes -- everywhere it matters not just "what happened"
but "exactly when, and how confident we are in that."

## Relative Timeline / T0-Anchor (Proposed in Discussion)

In addition to per-source offset/uncertainty, a complementary idea for specific event
chains (e.g., a single PaymentIntent): **a T0 reference point for that specific chain**,
not only global Z(t).

### Event Record Model

    record = {
        z_recorded:      Z_now() at moment of Secretariat fixation --
                          IMMUTABLE fact "we observed this then
                          by our clock"; never corrected
                          under external offset
        external_claim:  timestamp claimed by external party
                          (optional, if applicable)
        offset:          external_claim - z_recorded
        uncertainty:     +/- per offset measurement method
    }

z_recorded is never rewritten to match external_claim -- offset is stored as an
annotation over the fact, not a replacement of the fact.

### T0 and Relative Time Within a Chain

For reasoning about a specific operation (SLA, timeout, staleness), what matters is
not absolute position in time but **elapsed time since the start of THIS specific chain**:

    T0 = z_recorded of first event in chain
         (for payment lifecycle -- likely candidate: offerReceivedAt,
         already established as mandatory durable field for
         staleness guard in B8.1-B.2)

    Each subsequent event carries:
        z_recorded            -- absolute position (audit, Notary,
                                 cross-operation correlation)
        dt = z_recorded - T0  -- relative position within THIS
                                 specific chain (timeout/SLA/
                                 staleness logic)

This structurally matches distributed tracing models (span-based tracing: trace has
start time, all events carry offset from it) -- an independently derived solution to
the same problem already established in another engineering domain.

**Important implication for future implementation:** offerReceivedAt in this model
is not merely input for one staleness check (as decided for B8.1-B.2), but a potential
canonical T0 for the entire payment operation event chain: signing, settlement, seller
response, reconciliation could all be measured relative to it. This does not change the
B8.1-B.2 decision -- offerReceivedAt remains exactly what it already is -- but it is a
natural extension of the same data point when Temporal Evidence becomes relevant.

## What NOT To Do Now

* Do not build offset/uncertainty mechanism within B8.1-B.2 scope.
* Do not attempt to "correct" client time for EIP-3009 authorization signing.
* Do not expand current reconciliation/evidence code scope for this -- wait for a
  dedicated architectural block when it reaches roadmap priority.

This section exists so the principle is not lost between chat messages -- not as a task for execution.
