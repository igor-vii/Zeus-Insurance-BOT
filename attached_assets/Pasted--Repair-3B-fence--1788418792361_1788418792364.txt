Вывод по lock race

Это закрывает именно ту гонку, ради которой мы отвергли #3A:

A: BEGIN A: SELECT recovery_jobs FOR UPDATE, fence=N A: recovery mutation A: recovery INSERT A: requeue/close A: COMMIT B: claimJob() ↓ UPDATE той же recovery_jobs row ↓ ждёт COMMIT A ↓ получает уже новое состояние

То есть B не может вклиниться между проверкой fence и recovery INSERT. Это принципиально важно.

ВАЖНО:
Не проектируй другой вариант и не заменяй решение простыми early-return.
Главная цель #3B — атомарно связать проверку текущего fence_generation с созданием recovery action.

Требуемый механизм:

PostgreSQL createRecoveryAttemptIfOwner():

одна DB transaction;

SELECT ... FROM recovery_jobs WHERE job_id = ... FOR UPDATE;

проверить status=RUNNING и fence_generation=N;

проверить исходный attempt;

ATTEMPTED → DELIVERY_UNKNOWN;

INSERT retry attempt;

requeue recovery job;

COMMIT.

PostgreSQL createRecoveryJobIfOwner():

одна DB transaction;

SELECT recovery_jobs ... FOR UPDATE;

проверить ownership/fence;

ATTEMPTED → DELIVERY_UNKNOWN;

INSERT retrieval job;

закрыть исходный EXECUTION job;

COMMIT.

claimJob() уже является одним атомарным:
UPDATE recovery_jobs ... fence_generation = fence_generation + 1 ... RETURNING fence_generation.
Поэтому row lock на recovery_jobs должен сериализовать claim и recovery creation.

InMemory должен иметь поведенческую parity:
ownership check + все соответствующие mutations должны выполняться синхронно, без await между ними.

Production processJob() не должен после нового atomic primitive дополнительно выполнять старые saveAttempt() / saveJob() для того же recovery action.
Никаких двойных recovery inserts.

C. Lock ordering:
найди все production места, где одновременно блокируются/изменяются recovery_jobs и execution_attempts.
Нужно убедиться, что нет production path с обратным порядком:
execution_attempts → recovery_jobs
против:

который может создать PostgreSQL deadlock.
Если такого path нет — зафиксировать это как PASS.
Если есть — НЕ исправлять самостоятельно, а остановиться и сообщить точное место.
